HELLO-DEVOPS (plain-English version of README.md)

WHAT IT IS
A tiny web service written in Python. It answers "am I healthy?" questions and has a secret switch that can deliberately make it look sick, so you can watch the cloud notice and react. It runs on Amazon Web Services (AWS) and is deployed automatically by GitHub every time code is pushed to the branch called prod-hardening.

HOW IT FITS TOGETHER
You push code to GitHub. GitHub proves who it is to AWS using a short-lived pass (no passwords or keys are stored anywhere). It checks the code, builds a container image, stores it in AWS's image shelf (ECR), then uses Terraform (a tool that builds cloud things from text files) to create or update everything, and finally tests the live website. The website sits behind a load balancer that spreads visitors over two copies of the app. Logs go to CloudWatch. Alarms watch for errors.

WHAT YOU NEED
To run it on your computer: Python and optionally Docker. To deploy: the AWS command line logged in to the right account, Terraform version 1.10 or newer, and the GitHub command line. No AWS keys are needed for the automatic pipeline.

HOW TO USE IT
On your computer: make test runs the 17 tests. make run starts the app on port 8080 with the secret switch password set to "local".
On AWS: make bootstrap once (creates the storage for Terraform's notes, the image shelf and the pass GitHub uses). After that, pushing to prod-hardening or running make rebuild deploys everything. Scripts in mac-scripts and win-scripts break the app, fix it, show status and show logs. The Windows scripts were written to match the Mac ones but were not run on Windows.
To remove everything: make destroy, then make destroy-bootstrap last.

WHAT THE APP DOES
- The home page says who it is, which version it is and whether it is ok or degraded.
- /livez says the program is running.
- /healthz says healthy or not. It fails (503) while the app is deliberately broken.
- /readyz says ready or not. It fails when broken, and also while the app is shutting down so visitors are moved away first.
- /admin/chaos is the secret switch. It needs a password (a bearer token kept in AWS's secret store). Wrong or missing password gets 401. Bad input gets 400, oversized input gets 413.
- Every answer carries basic browser safety headers and a request ID. Logs are one JSON line per request.

TESTS
17 automated tests start the real server and check all of the above, with a pretend AWS. No network needed. To be sure the tests actually guard something, seven different pieces of protection were removed one at a time (password check, break handling, shutdown handling, size limit, input check, disabled-admin rule, safety headers) and every time the tests failed as they should; each edit was then put back.

DESIGN CHOICES THAT ARE NOT OBVIOUS
- The broken/ok flag lives in one shared AWS parameter, so breaking affects both copies of the app and survives a restart. The side effect is that while broken, AWS keeps replacing the sick copies, which you can see in the timeline.
- No NAT gateway (a paid network box) is used, to save money. The app copies have public addresses but only accept traffic from the load balancer.
- The website is plain HTTP only. There is no domain name or certificate, so this is not fully production grade.
- The image shelf and the Terraform notes bucket are made by hand first because the automatic pipeline needs them before it can run.
- The admin password is generated by Terraform, so a copy also sits in the private, encrypted Terraform notes bucket.

WHAT WAS PROVEN ON AWS (2026-10-20), THEN TORN DOWN
The stack was verified live on 2026-10-20 and then deleted the same day to save cost. The old web address no longer answers. To rebuild: run make bootstrap once, then make rebuild. The address will be new. What was removed: the whole main stack, then the Terraform notes bucket, image shelf and GitHub pass. Shared items (the GitHub login provider and the permission-limit policy) were not touched. AWS keeps empty INACTIVE records of the container cluster and old task definitions for a while; these cost nothing.
Evidence from while it was live:
- The GitHub pipeline ran from the prod-hardening branch and succeeded (run 39389376156): checks, build, deploy of 40 resources, and the smoke test. A second push (run 39389403002) also deployed successfully as a rolling update.
- The live address answered: home page 200, healthz 200, readyz 200, livez 200, unknown page 404, admin without password 401.
- Break test: at 13:03:56 the break script was run. Health went to 503 straight away. About 30 seconds later the load balancer marked both copies unhealthy and AWS started replacing them (the replacements were also broken, as designed). The synthetic checker alarm fired at 13:06:57, and by 13:07:31 all three alarms (5xx errors, unhealthy copies, synthetic check) were in alarm.
- Recover test: at 13:07:37 the recover script was run. Health returned to 200 immediately, both copies were healthy again, and the alarms went back to OK over the next few minutes (alarm data lags by a minute or two).
- What exists in AWS: a private network, a load balancer, a container cluster with two small app copies, three roles, two stored parameters, two log groups, an alert topic, three alarms, and a small checker function that tests the site every minute. While running, the estimated cost was about 9 US cents an hour (an estimate from price lists, not a bill).

WHAT WAS NOT PROVEN
- The automatic roll-back when a bad version is deployed is set up but nobody pushed a bad version to watch it happen.
- Alert emails: the alert topic has no subscriber, so alarms are visible in the AWS console but nothing is sent.
- Behaviour under heavy load, the Windows scripts, and anything visual (the service only returns text, and everything was checked with curl).

SECRET NOTE
The original repo had a committed .env file with one setting, REQUIRED_TOKEN, whose value is a single digit. It is not a real credential. It is now removed from tracking and ignored, but it still exists in old git history.
